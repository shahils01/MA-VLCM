# Square return error and next training experiments

The displayed `square_success.mp4` uses `outputs/zero_margin_900/best.pt`, epoch 5. Its configuration is frozen SmolVLM, 128-pixel processor size, 6 frames at 5 Hz (1.0 seconds of history), and full 20 Hz control-step returns with gamma 0.99. It used a 900-episode subset, with train/validation/test episode splits. The backbone was frozen; the graph, visual projection, fusion, temporal Transformer and scalar head were trained.

The successful square example has nonterminal MSE 0.68363. At 7.8 seconds the recorded future return is +0.70790 and the stored prediction is -0.94531. At 9.2 seconds the values are +0.98942 and -0.58594. Fresh CPU inference from the same checkpoint with its cached VLM features reproduced the error: -0.94278 at 7.8 seconds and -0.60473 at 9.2 seconds. Maximum difference from stored bfloat16 predictions was 0.01880, far smaller than the return error. Thus the oscillation is not introduced by the video replay or bfloat16 rounding. Full validation/test reward labels were also checked against the raw control rewards in the prior report.

Aggregate validation MSE is 0.09136. Successful validation clips have MSE 0.15168, compared with 0.06975 for failed clips. Successful test clips have MSE 0.20139. These metrics make clear that a favorable aggregate number can mask poor behavior on successful trajectories. A single episode is not sufficient to identify a cause or select hyperparameters.

A Monte Carlo target is one episode's realized return. A value function estimates conditional expected return; it cannot be required to anticipate every realized success/failure perfectly. The current model fits a behavior mixture of initial/intermediate actors without policy identity as an input. Similar recent observations can have different future outcomes. This explains possible irreducible variance, but does not excuse the large errors on this example or establish the cause of its oscillation.

## Recommended order

1. Keep the new 60 seeded episodes outside all training splits. Use them as external validation for all candidate checkpoints. Once used repeatedly for model selection, they are validation rather than an untouched final test. Report per-formation and per-outcome metrics plus episode-averaged errors, not just clip-weighted aggregate MSE.
2. Use the now-complete 2,000-episode full-control-reward collection and check its coverage before treating episode count as the fix. The older 2,000-episode collection has no full control reward streams, different workspace bounds, and sampled-proxy return labels. Its MSE is not directly comparable with the orange run or these new archives. The current `formation_vlcm_polygon_3to6_10hz_inner00m` collection now has 2,000 episodes (125 per stage/team-size combination); the saved 903-episode audit was stale. Use this full-reward collection with `--return-source control` and `--max-episodes 0`. Do not combine it silently with the older sampled-reward collection. Include successful squares/hexagons, recoveries, near-boundary states and failed trajectories; do not discard failures to make the plotted target smoother.
3. Compare frozen and LoRA runs with identical dataset, episode split seed, return definition, image rate/resolution and context length. The existing trainer supports `--backbone-mode lora` and rank-8 adapters in language-model q/v projections; it does not currently adapt the vision encoder. Try a lower learning rate such as 3e-5 as a candidate, with validation-based early stopping. This is an experiment, not a demonstrated improvement. Full-backbone fine-tuning is a more expensive later comparison and can overfit.
4. Increase temporal history as a separate experiment. The existing CLI supports 6 or 8 frames: 8 frames at 5 Hz span 1.4 seconds. A 16–32 frame window at 5 Hz would span 3–6.2 seconds and requires expanding that CLI restriction and measuring memory. Increasing image rate while keeping the same frame count shortens the history in seconds. Keep this change separate from the frozen/LoRA comparison.
5. Evaluate a graph/state-only baseline and a VLM-feature ablation before attributing gains to the VLM. For a specified deployment actor, train/evaluate a policy-specific value (`--policy-stage intermediate` is available). If the actual objective is policy-mixture value, retain the mixture and its natural held-out distribution. Oversampling successes changes the effective target distribution unless importance weighting or another explicit correction preserves it.
6. If large adjacent-frame changes remain, experiment with a small interval-aware temporal/Bellman consistency term in addition to Monte Carlo regression. For adjacent image anchors use the complete interval reward R and gamma**m, where m is the number of control steps. This needs new paired-clip training code and tuning; blindly penalizing all changes can erase real terminal/collision transitions. Do not smooth the recorded rewards or impose monotonic predicted returns as a general rule.

The next simple comparison is a frozen versus rank-8 LoRA run on the completed 2,000-episode full-reward collection, holding the other settings fixed. Expanding from the prior 900-episode subset changes the internal split membership, so use the same fresh 60 external episodes for comparisons rather than treating the old internal-validation MSE as directly comparable. Select using per-formation/outcome validation errors; examine trajectories after selection. No new training job was started as part of this analysis.

References: [value function and expected return](https://spinningup.openai.com/en/latest/spinningup/rl_intro.html), [LoRA paper](https://arxiv.org/abs/2106.09685). These motivate definitions and adaptation, not an empirical guarantee for this dataset.
